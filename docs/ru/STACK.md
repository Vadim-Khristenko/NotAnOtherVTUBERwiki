# Стек

Русская версия. Английская: [STACK.md](../STACK.md)

У каждой технологии здесь есть причина, и каждая версия проверена по crates.io, npm или
официальным релизам на 30.08.2026. Ничего в этом файле не взято из памяти.

Здесь объясняется **почему**. Если вам нужно **что и когда мы строим**, читайте
[ROADMAP.md](../ROADMAP.md).

## Одно решение, которое важнее остальных

**Мы рендерим по записи и отдаём при чтении.**

Почти все вики в мире рендерят страницу в момент запроса. Поэтому они медленные, и
поэтому им нужно столько железа. Мы делаем наоборот.

```text
ПУТЬ ЗАПИСИ (асинхронно)          ПУТЬ ЧТЕНИЯ (синхронно, только Rust)
  сохранили или опубликовали        GET /wiki/Page
      |                                  |
  джоба рендера в очереди           поиск в render_cache по хешу контента
      |                                  |
  пайплайн Markdown (Rust)          HTML, ETag, Brotli, готово
      |
  SSR компонентов (Bun-воркер)
      |
  санитизация, кеш, готово
```

Последствия это и есть суть проекта:

- Попадание в кеш это поиск и ответ. Никакого парсинга Markdown, никаких шаблонов,
  никакого похода в базу за контентом.
- Промах кеша рендерит в фоне. Читатели продолжают получать предыдущую, полностью
  валидную версию и никогда не ждут.
- Bun-воркер, самая тяжёлая часть системы, доступен только из фоновой джобы. Если он
  упал, тормозит или не установлен, чтение не страдает.
- Публикация шаблона ставит в очередь перерендер ровно тех страниц, которые от него
  зависят, а не всего кеша.

Всё остальное в этом файле работает на это.

## Слой отдачи: Rust

| Выбор | Почему |
|-------|--------|
| **Rust, edition 2024** | Безопасная работа с памятью без сборщика мусора, абстракции с нулевой ценой и максимально предсказуемые хвостовые задержки. Путь чтения это основная часть трафика и там наши самые жёсткие обещания. |
| **Axum 0.8.9** | Построен на Tower и Tokio, поэтому доступна вся экосистема middleware. Экстракторы делают хендлеры чистыми. Это самый скучный хороший выбор в Rust-мире, а скука это фича. |
| **Tokio 1.53.1** | Стандартный асинхронный рантайм с планировщиком, который крадёт работу. |
| **MiniJinja 2.24.0** | Совместим с Jinja2, песочница, хот-релоад в разработке. Скины это шаблоны MiniJinja, поэтому автору скина не нужно знать Rust. |
| **pulldown-cmark 0.13.4** | CommonMark плюс расширения, которыми реально пользуются: таблицы, сноски, списки задач. |
| **ammonia 4.1.4** | Санитайзер HTML по белому списку. Через него проходит каждый путь, который produces HTML. |
| **TailwindCSS 4** | JIT-компиляция, сначала тёмная тема, а плагин Typography оформляет отрендеренный Markdown. |

Почему не Node или Bun для слоя отдачи? Bun 1.4.0 правда хорош и теперь написан на Rust,
см. раздел про воркер. Но он всё ещё исполняет JavaScript на JavaScriptCore, а значит на
горячем пути есть сборщик мусора. Отдача кешированного HTML это поиск и ответ. Rust
делает это без кучи, которую надо собирать, и без пауз аллокатора, которые надо прятать.
На Raspberry Pi эта разница и есть весь бюджет.

## Слой данных: PostgreSQL 18

Одна база делает пять работ вместо пяти баз, каждая из которых делает одну.

| Работа | Как |
|--------|-----|
| Реляционное ядро | Страницы, ревизии, пользователи, роли, категории, редиректы |
| Гибкие метаданные | JSONB для настроек вики и конфигурации плагинов |
| Полнотекстовый поиск | `tsvector` плюс `pg_trgm` для опечаток, без отдельного сервиса |
| Кеш и очереди | в паре с Valkey на горячих путях |
| Изоляция | Row level security как вторая линия обороны послеフィルтров приложения |

Почему не MongoDB? Вики глубоко реляционные: у страниц есть ревизии, у ревизий авторы, у
категорий родители, у шаблонов зависимые. Документное хранение это неправильная форма.

Почему не SQLite? Она отличная, и когда-нибудь мы, возможно, добавим её для установок на
одного пользователя, но полнотекстовый поиск, индексы по JSONB и параллельные писатели
между репликами там заметно сложнее.

**SQLx 0.9.0** с проверяемыми на этапе сборки макросами означает, что опечатка в запросе
это ошибка компиляции, а не ночный вызов. Цена в том, что сборке нужна схема базы, и мы
решаем это закоммиченной папкой `.sqlx` и `SQLX_OFFLINE=true` в CI.

## Слой кеша: Valkey 9.1.1

Valkey это комьюнити-форк Redis, и он используется для сессий, кеша рендера, счётчиков
лимитов и очереди джоб рендера.

Почему Valkey, а не Redis? Он активно развивается под по-настоящему открытой моделью
управления и совместим по протоколу, поэтому любой Redis-клиент работает без изменений.
Версия 9.1.1 важна конкретно тем, что это security-релиз, закрывающий use-after-free при
обработке TLS-соединений.

Valkey ещё и причина, по которой веб-слой может быть без состояния. Сессии и кеш живут вне
процесса, поэтому любая реплика отвечает на любой запрос, а реплики можно добавлять
свободно.

## Модель контента: неймспейсы и трансклюзия

Это то, что большинство вики-движков делают неправильно, и то, что нам важнее всего.

Большинство Markdown-вики дают плоский список страниц. Настоящие фанатские вики работают
на шаблонах: один инфобокс, правится один раз, подключается на сотни страниц. Если
шаблоны лежат в файлах, их правка это деплой. Мы кладём их в базу.

| Неймспейс | Назначение |
|-----------|------------|
| `Main` | Статьи |
| `Talk` | Обсуждение, привязанное к странице |
| `Template` | Переиспользуемая разметка, подключается как `{{Имя\|арг=значение}}` |
| `Module` | Интерактивные компоненты на TypeScript или Vue SFC |
| `File` | Страницы описания медиа |
| `User` | Домашние страницы пользователей |
| `Project` | Политики и справка |
| `Category` | Страницы категорий |

Предохранители, которые делают это безопасным: глубина подключения ограничена, циклы
обнаруживаются и разрываются видимым маркером, правка `Template:` и `Module:` требует
повышенных прав, потому что одна плохая правка ломает все страницы, которые их
подключают, а граф зависимостей означает, что публикация шаблона инвалидирует ровно те
страницы, которые его используют.

## Компоненты: админы могут собирать настоящие виджеты

В MediaWiki добавление интерактивного виджета это написать PHP и найти того, кто это
задеплоит. У нас админ пишет компонент в браузере.

```vue
<script setup lang="ts">
interface Props { name: string; avatar?: string; debut?: string }
const props = defineProps<Props>()
const expanded = ref(false)
</script>

<template>
  <aside class="infobox">
    <img v-if="avatar" :src="avatar" :alt="name">
    <h3>{{ name }}</h3>
    <button class="more" @click="expanded = !expanded">Details</button>
  </aside>
</template>
```

Пайплайн сборки:

1. Сохранение в неймспейсе `Module:` как новой неизменяемой версии.
2. Компиляция и сборка через **rolldown 1.2.6**: получаются SSR-бандл и клиентский бандл.
3. Серверный рендер в воркере, санитизация в Rust, кеширование.
4. Отдача с SRI-хешем, загрузка только на тех страницах, где он используется, и только
   если доступен JavaScript.

Итого компонент полностью виден поисковикам и читателям с выключенным JavaScript и
становится интерактивным, когда JavaScript есть. Тот же контракт прогрессивного
улучшения, что и у всего движка.

Есть второй, более простой вариант под названием `plain-ts`: одна функция
`render(props): string`, которая исполняется во встроенном в Rust JavaScript-движке. Он
нужен, чтобы установка вообще без воркера тоже получила компоненты, пусть и с потерей
синтаксиса и интерактивности.

## Слой воркера: Bun 1.4.0

Bun это асинхронный воркер. Он никогда не на пути запроса.

**Bun 1.4.0 написан на Rust.** Это не слух, это заголовок официального поста о релизе от
20.08.2026. Это снимает главное возражение против второго рантайма в Rust-проекте: второго
тулчейна, о котором надо думать, нет, потому что оба на Rust.

Что делает воркер:

| Работа | Встроенное API |
|--------|----------------|
| Сборка компонентов | rolldown плюс компилятор Vue SFC |
| Серверный рендер компонентов | Vue SSR |
| Рендер схем | `Bun.WebView`, headless, заменяет Puppeteer |
| Миниатюры картинок и WebP или AVIF | `Bun.Image`, заменяет sharp |
| Планировщик: дайджесты, прогрев кеша, реиндекс | `Bun.cron()` |
| Инструменты импорта и экспорта | плюс `Bun.markdown` там, где не важна консистентность |

Проверенные цифры из официального поста, процитированные, а не придуманные: старт на
Linux 5.1 мс против 10.9 мс у Bun 1.3 и 27.2 мс у Node.js 26, idle CPU в 5 раз ниже, чем у
Bun 1.3, и `Bun.serve` с пиком 36 МБ под нагрузкой.

Две вещи, в которых хотим быть точными, потому что их легко перепутать:

- Bun всё ещё исполняет JavaScript на **JavaScriptCore**, поэтому сборщик мусора никуда
  не делся. mimalloc улучшает возврат памяти, но не убирает сборку. Вот настоящая причина,
  по которой воркер остаётся вне пути запроса.
- `bun build --compile --asset` умеет упаковать воркер и его ассеты в один исполняемый
  файл, поэтому на хосте не нужен ни Node, ни Bun.

`Bun.markdown` намеренно не используется для статей. `naw-markdown` с pulldown-cmark это
единственный источник правды, чтобы веб-слой, CLI, воркер и предпросмотр в редакторе
никогда не расходились в том, как выглядит страница.

## Слой авторства: Vue 3 и Vite

| Выбор | Версия | Почему |
|-------|--------|--------|
| Vue 3 | 3.5.42 | Редактор, админка, редактор компонентов и редактор скинов |
| Vite | 8.2.2 | Собирает в обычную статику, которую отдаёт Rust |
| TipTap | 3.30.5 | Блочный редактор на ProseMirror: таблицы, вставки, отмена, позже совместная работа |
| rolldown-vite | 7.3.1 | Rust-бандлер под Vite, то же ядро, что и в пайплайне компонентов |

Мы отказались от первоначальной идеи писать редактор на Rust с компиляцией в WebAssembly.
Его сильные стороны это серверный рендер и гидрация, а мы не используем ни то, ни другое,
потому что путь чтения это Rust и ноль JavaScript. Нам нужен клиент со
встроенным текстовым редактором, библиотекой форм, drag-and-drop и доступными
компонентами. Писать всё это с нуля на Rust это месяцы ради результата хуже, чем уже есть
у Vue.

Приложение авторства загружается только когда кто-то нажал Edit или открыл админку. На
пути чтения его нет.

## Интерфейсы, которые остаются заменяемыми

Три возможности сидят за Rust-трейтами, поэтому установка платит только за то, что
использует.

| Трейт | По умолчанию | Альтернативы |
|-------|--------------|--------------|
| `SearchBackend` | Полнотекстовый поиск PostgreSQL | Meilisearch 1.53.1, Tantivy 0.26.1 |
| `StorageBackend` | Локальный диск | Любое S3-совместимое хранилище через object_store 0.14.1 |
| `DiagramBackend` | Mermaid в `Bun.WebView` | graphviz, PlantUML |

Вика на одной ноде запускает PostgreSQL и больше ничего. Большая добавляет Meilisearch и
S3. Код приложения не меняется.

## Что мы сознательно не выбрали

| Не выбрали | Почему |
|------------|--------|
| Leptos или любой фронтенд из Rust в WASM | Его SSR и гидрация тут не нужны, а экосистемы блочного редактора и админки на Rust нет |
| Meilisearch как единственный поиск | Это вторая база, которую надо поднимать, и она не вписывается в цель Raspberry Pi |
| MinIO как обязательная зависимость | Вике на одной ноде не нужно шесть контейнеров, чтобы положить PNG |
| Redis вместо Valkey | Valkey это активно развивающийся форк под открытым управлением, и он совместим по протоколу |
| Плагины на WASM | Месяцы работы на песочницу и права ради интеграций, которые уже покрывают компоненты |
| Node.js для воркера | Bun стартует на Linux в 5.3 раза быстрее и везёт встроенные API, которые иначе пришлось бы ставить |
| Микросервисы везде | Три слоя с понятными границами, а не пятнадцать сервисов |

## Как это масштабируется

У каждого слоя свой конверт ресурсов, своё количество реплик и свой домен отказа.

```text
                     читатели (почти весь трафик)
                                |
                   [ Caddy или CDN: Brotli, HTTP/3 ]
                                |
                 +--------------+--------------+
                 |                             |
      [ naw-web: N реплик ]          [ worker: M реплик ]
        Rust, Axum, stateless          Bun 1.4.0, async
        кешированный HTML и API        сборка, SSR, схемы
                 |                             |
                 +------+---------+------------+
                        |         |
               [ PostgreSQL 18 ] [ Valkey 9 ]
                                       |
                        [ объектное хранилище: диск или S3 ]
```

- `naw-web` без состояния. Сессии, кеш и очереди живут в Valkey, поэтому любая реплика
  отвечает на любой запрос.
- Воркер доступен только через очередь. Добавить воркеров это поменять число реплик.
- Результат рендера адресуется по контенту, поэтому его может произвести любой воркер, а
  отдать любая веб-реплика.
- Вообще без воркера мы отдаём устаревший, но корректный HTML, а не страницу ошибки.
